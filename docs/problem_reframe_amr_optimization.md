# 문제 재정의 — "AMR 도입 정당화"에서 "AMR 운영 최적화"로

> 작성: 2026-06-21 | 대상: 팀 공유용
> 선행 문서: [transport_fab_decoupling.md](transport_fab_decoupling.md) (디커플 검증 상세)

---

## TL;DR

- **발견**: 이 fab은 장비병목 + WIP버퍼라, 반송 디스패칭(FA/OHT/AMR, 차량 20~76대)이
  **fab 처리량·납기에 영향을 주지 않음**(검증 완료, 선행 문서).
- **그래서 막힘**: "반송을 최적화하면 fab이 좋아진다"는 주장이 데이터상 거짓.
  여기서 "HOT을 쪼들리게 만들어 FA가 이기게 하자"는 유혹이 있었으나 → **그건 조작**
  (문제를 방법에 맞추는 것).
- **재정의(이 문서)**: **AMR 전환을 전제로 두면**, 질문이 "AMR을 도입할까?"가 아니라
  **"이미 AMR을 쓰는데 어떻게 잘 굴릴까?"** 가 됨. = AMR 시스템 *자체*의 운영 최적화.
- **정직 조건**: 목적함수를 **fab 처리량이 아니라 transport-layer 효율**로 둘 것.
  (디커플을 부정하지 말고 *인정한 채로* AMR 운영을 최적화)

---

## 1. 우리가 부딪힌 벽

전체 흐름:
1. FA(RL 디스패처)가 실 대수(50·76대)에서 nearest 휴리스틱을 못 이김.
2. 비교를 OHT(기존 반송)로 확장 + 반송지연이 fab에 닿도록 **루프를 닫음**(closed-loop).
3. 결과: 차량을 20대까지 굶겨 반송을 반토막 내도 **fab 일정(CR)·진행 불변.**
4. 원인 = **장비병목(Diffusion oversubscribed) + WIP버퍼**. 장비 앞에 늘 일감이 쌓여
   있어 반송이 느려도 장비가 안 쉼 → fab 처리량 = 장비용량, 반송과 무관 (제약이론).

→ "반송 최적화 → fab 개선"은 이 데이터에서 **구조적으로 거짓**.

## 2. 빠질 뻔한 함정

막히자 "HOT 비율을 올리거나 HOT 납기를 조여서 FA가 이길 판을 만들자"는 안이 나왔음.
**이건 (b) 조작** — 데이터가 부족한 게 아니라, 데이터가 "여기선 반송이 안 중요하다"는
정직한 답을 주는데, RL을 정당화하려고 문제를 비트는 것. 연구 안티패턴.

## 3. 재정의 — 전제를 바꾸면 질문이 바뀐다

> **AMR 기반 반송으로의 전환 자체를 전제(given)로 둔다.**

그러면 우리가 풀 문제는:
- ❌ "AMR을 도입하면 fab이 좋아지는가?" (도입 정당화 — 디커플이라 답이 '아니오')
- ✅ **"이미 AMR을 쓰는 fab에서, AMR을 어떻게 최적 운영하는가?"** (운영 최적화)

이건 실무가 OHT→AMR 전환 시 실제로 푸는 문제(AGV/AMR dispatching, traffic management,
fleet sizing)이고 — **fab 처리량과 별개로 그 자체의 가치**가 있음.

## 4. 정직 조건 — 단 하나

**목적함수를 "fab 처리량"이 아니라 "transport-layer 효율"로 둘 것.**
우리가 증명한 디커플을 *부정하지 않고 받아들인 채*, AMR 시스템 자체를 최적화한다:

| 목적 | 왜 real한가 |
|---|---|
| **Deadlock / 혼잡 강건성** | AMR 시스템 멈춤(deadlock 캐스케이드)은 실제 실패. 처리량이 장비병목이어도 별개 문제. |
| **Fleet 효율 / 비용** | 같은 서비스를 더 적은 차·짧은 이동·적은 에너지로. AMR은 비싸므로 real CapEx/OpEx. |
| **서비스 수준 (HOT 지연)** | 긴급 lot 납기 보장. 단 **제약조건(SLA)**으로 — 인위적 병목으로 만들지 않음. |

→ **"fab을 더 빠르게"라고 주장하지 않는 한 전부 정직한 목적.**

## 5. 이 재정의가 살리는 것

- **초기 FA 결과(20대: deadlock −32.5%)가 다시 유효.** 그건 독립 반송 sim의 transport-layer
  지표였고 "fab 전파 안 됨"으로 폐기했었음 → 목적을 transport-layer로 두면 **정확히 우리가
  원하던 증거**(FA가 AMR 시스템을 더 강건하게).
- **디커플 발견은 버리는 게 아니라 "scoping 기여"로 살아남음**: "우린 fab 처리량 개선을
  주장하지 않는다 — 그건 장비병목이라 디커플임을 보였고, 대신 AMR 운영 효율을 최적화한다."
  reviewer가 신뢰하는 정직한 범위 설정.

## 6. 바뀌는 것 — 지표와 보상

**평가 지표** (fab CR 폐기 → transport-layer):
- deadlock / 1000스텝, 혼잡(점유충돌·재경로), 평균 이동거리·에너지
- 필요 fleet 크기 (목표 서비스 충족 최소 대수)
- HOT SLA 충족률 (제약)

**보상함수 (방향):**
```
reward = − w_dl  · deadlock              ← AMR 강건성 (FA 실증 우위)
         − w_cong· 혼잡(점유충돌·대기)      ← 흐름 효율
         − w_trav· 총 이동거리/에너지        ← fleet 효율
         − w_hot · HOT 지연 (SLA 제약)       ← 서비스 수준
         (fab throughput 항 없음 — 디커플 인정)
```

## 7. 정직한 남은 숙제 (조작 아님)

목적이 real이 됐어도, **FA가 그 transport-layer 목적에서 휴리스틱을 *일관되게* 이기는지**는
아직 미확정 (deadlock 우위가 50·20대 O, 76대 X로 들쭉날쭉). 다음 실험:

> transport-layer 목적 중 **FA가 휴리스틱을 일관되게 이기는 지점/목적**을 찾기.
> "이기는 판을 만든다"가 아니라 "real 목적에서 어디가 강한지 측정한다."

## 한 줄 요약 (팀 공유용)

> **"AMR을 도입하면 fab이 빨라진다"(거짓·디커플)가 아니라, "AMR 전환을 전제로, AMR 운영을
> RL로 최적화한다"로 문제를 재정의. 목적은 fab 처리량이 아니라 transport-layer 효율
> (deadlock 강건성·fleet 효율·HOT SLA). 디커플 발견은 정직한 범위 설정으로 함께 보고.**
